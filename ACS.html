1. Background & Limitations

Currently, the identity provider for the Salesforce Experience Cloud site is Azure AD B2C. By default, Azure AD B2C uses Microsoft's shared internal servers (e.g., msonlineservicesteam@microsoftonline.com) to send One-Time Passcode (OTP) verification emails.

The Problem: The default Microsoft email infrastructure acts as a "black box." It is impossible to retrieve delivery logs, bounce rates, or spam filter rejections for these emails. If a user fails to receive an OTP, administrators have no way to troubleshoot.

To enable detailed delivery tracking, we must bypass the standard emails and route B2C verification codes through a custom REST API using Azure Communication Services (ACS).

2. Architecture Overview

Because Salesforce acts only as the Relying Party (waiting for the login to complete), 100% of this implementation resides within the Azure ecosystem. No Salesforce API limits are consumed.

  1. Trigger: User attempts to log into the Salesforce Experience Site and is redirected to Azure AD B2C.
  2. OTP Generation: Azure AD B2C generates the verification code.
  3. API Callout: B2C Custom Policies (XML) make a RESTful POST request containing the User's Email and the Code to an Azure Function.
  4. Email Dispatch: The Azure Function utilizes the Azure Communication Services (ACS) SDK to send the email.
  5. Log Tracking: ACS automatically pushes the delivery status (Delivered, Bounced, Failed) to an Azure Log Analytics Workspace.
  6. Completion: The user enters the code into B2C, is authenticated, and redirected back to Salesforce successfully.

3. Cost Analysis

This serverless architecture is highly cost-effective and utilizes Azure's Pay-As-You-Go pricing model.

Service Purpose Estimated Cost
Azure Functions Hosts the custom REST API ~$0.00 (First 1 Million executions per month are FREE on the Consumption plan)
Azure Communication Services Sends the actual emails ~$0.00025 per email (e.g., $2.50 for 10,000 emails)
Azure Log Analytics Stores the delivery logs ~$2.00 - $3.00 per GB (Email logs are tiny text files; expected cost is pennies per month)
Salesforce Experience Cloud Host $0.00 (No Salesforce resources/API calls are used for this process)

4. Step-by-Step Implementation

Step 4.1: The Azure Function (REST API)

Create an Azure Function (Node.js) on a Consumption Plan. This acts as the middleman between B2C and ACS. We use the official Azure ACS Email SDK instead of raw SMTP for better reliability and performance.

const { EmailClient } = require("@azure/communication-email");

module.exports = async function (context, req) {
    // 1. Grab the email and code sent by Azure AD B2C
    const userEmail = req.body.email;
    const otpCode = req.body.verificationCode;

    // 2. Connect to your ACS Resource via Connection String
    const connectionString = process.env.ACS_CONNECTION_STRING;
    const emailClient = new EmailClient(connectionString);

    // 3. Construct the email payload
    const message = {
        senderAddress: "DoNotReply@yourdomain.com",
        content: {
            subject: "Your Salesforce Login Code",
            plainText: `Your verification code is: ${otpCode}`,
        },
        recipients: {
            to: [{ address: userEmail }],
        },
    };

    try {
        // 4. Send the email and wait for completion
        const poller = await emailClient.beginSend(message);
        await poller.pollUntilDone();
        
        // Return 200 OK back to B2C
        context.res = { status: 200, body: "Email sent successfully" };
    } catch (error) {
        // Return 409 Conflict if failed (B2C requires 409 for custom error handling)
        context.res = { status: 409, body: { userMessage: "Failed to send verification email." } };
    }
};

Step 4.2: Azure AD B2C Custom Policy (XML)

Update your B2C Custom Policy (specifically TrustFrameworkExtensions.xml) to include the RESTful Technical Profile. Replace the ServiceUrl with your published Azure Function URL.

<TechnicalProfile Id="SendVerificationEmail">
  <DisplayName>Send email via ACS API</DisplayName>
  <Protocol Name="Proprietary" Handler="Web.TPEngine.Providers.RestfulProvider, Web.TPEngine" />
  <Metadata>
    <!-- The URL of the Azure Function created in Step 4.1 -->
    <Item Key="ServiceUrl">https://my-b2c-email-api.azurewebsites.net/api/SendEmail</Item>
    <Item Key="SendClaimsIn">Body</Item>
    <Item Key="AuthenticationType">None</Item>
    <Item Key="AllowInsecureAuthInProduction">false</Item>
  </Metadata>
  <InputClaims>
    <!-- Payloads sent to the Node.js Req.Body -->
    <InputClaim ClaimTypeReferenceId="email" />
    <InputClaim ClaimTypeReferenceId="verificationCode" />
  </InputClaims>
  <UseTechnicalProfileForSessionManagement ReferenceId="SM-Noop" />
</TechnicalProfile>

Ensure this Technical Profile is referenced in your Orchestration Steps during the Sign-Up/Sign-In journey.

5. Enabling Tracking & Log Analytics

The primary goal of this architecture is to retrieve delivery logs. Here is how to configure and query them.

A. Enable Diagnostic Settings

  1. Navigate to your Email Communication Services resource in the Azure Portal.
  2. Go to Monitoring > Diagnostic settings.
  3. Click + Add diagnostic setting.
  4. Check Email Service Send Mail logs and Email Service Delivery Status Update Logs.
  5. Select Send to Log Analytics workspace and save.

B. Querying User Email Logs (KQL)

If a specific user reports a missing OTP code, navigate to your Log Analytics Workspace, click Logs, and execute the following Kusto Query Language (KQL) script to find the exact drop point:

ACSEmailStatusUpdateOperational
| where RecipientId == "user@theirdomain.com"
| project TimeGenerated, RecipientId, DeliveryStatus, DeliveryStatusDetails
| order by TimeGenerated desc

Expected Statuses: Delivered, Bounced, Failed, Suppressed. The DeliveryStatusDetails column will contain exact SMTP error codes from the receiving mail server (e.g., Blocked by Spam Filter).
